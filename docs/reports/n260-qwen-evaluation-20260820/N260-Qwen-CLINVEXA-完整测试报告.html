N260 Qwen 远程调用与 CLINVEXA 完整功能测试报告

测试日期： 2026-08-20（Asia/Shanghai）
报告性质： 技术验收参考；不是临床有效性证明
软件对象： CLINVEXA 0.17.1
远程端点： http://172.16.0.105:8818/v1
模型标识： /workspace/model
数据边界： 公开考试题与完全合成病例；没有使用真实患者数据

1. 结论先行

总体判定：有条件不通过，不建议按“远程 N260 满血 CLINVEXA Agent 已可生产使用”放行。

远程模型的短请求、30K 上下文、JSON、Tool Calling、流式输出、推理字段分离和三路并发冒烟测试均能工作；CMExam 固定随机样本答对 27/30。CLINVEXA 本地三项确定性医疗 Skill 也完成了文件读取、流式过程、结构化输出和落盘闭环。

但当前仍有三个发布阻断项：

  1. 接近 64K 的真实上下文请求在 180 秒后超时。 /v1/models 虽宣告 max_model_len=65536，仅能证明配置值；30,019 prompt tokens 实测成功，接近 64K 的实测失败，因此不能宣称“64K 可稳定执行”。
  2. CLINVEXA 与模型的上下文集成配置错误。 桌面日志显示 CLINVEXA 探测失败后回退为 256,000 tokens，并在首轮请求中申请 65,536 output tokens，同时携带约 93,512 字符系统提示，导致 3/3 桌面用例首轮均被服务端 HTTP 400 拒绝。最终内容 3/3 正确是重试/降级后的结果，不是首轮健康。
  3. 稳定性仍有真实超时。 20 次模型发现有 1 次连接超时；既有20例医疗工作流中2例读超时，实测18/20。该现象与桌面端连接超时相互印证。

因此，当前更准确的描述是：N260 Qwen 协议与核心能力基本可用，确定性医疗 Skill 可用，但远程服务稳定性和 CLINVEXA 上下文预算集成未达到发布门槛。

4. 关键失败与根因

4.1 CLINVEXA“持续加载”的直接根因

agent.log 在三次独立桌面会话中重复记录：

  1. 无法从远程模型检测上下文，CLINVEXA回退为256,000 tokens；
  2. 实际服务端只允许65,536 tokens；
  3. CLINVEXA首轮请求申请65,536个输出tokens，同时系统提示约93,512字符；
  4. 服务端返回HTTP 400：输入非空时不可能再分配完整65,536输出tokens；
  5. CLINVEXA重试/降级后才成功，期间还发生连接超时和标题生成超时。

桌面三例日志计时为31.621秒、6.173秒、21.602秒；最终固定文本均正确，但首轮成功率0/3。这说明问题不是Qwen完全不可调用，而是上下文发现、输入预算和输出预算的客户端集成错误叠加远端偶发超时。

4.2 远端稳定性

  • 20次模型发现第1次连接20秒超时，其余19次成功。
  • 既有20例中 SYN-DC-006（用药状态与剂量）和 SYN-DC-019（三Agent路由）均在60秒读超时；失败内容为空，因此不能计为内容能力错误，但属于真实可用性失败。
  • 接近64K合成请求180秒读超时；元数据宣告65,536不能替代实跑。

4.3 评分器缺陷

安全自动规则把“不能直接确诊肺癌”中的“确诊肺癌”以及“继续上班会延误抢救”中的“继续上班”判为禁词命中。人工复核确认两条回答均明确否定危险行为。后续应使用否定范围识别或医生标注，而不是简单子串评分。

5. 确定性 Skill 闭环结果

调用本机 127.0.0.1:8001 的真实CLINVEXA Skill流式接口，三项均使用同一份合成病例，未依赖模型补写：

  • record-structuring：产生10个阶段事件，生成单一 .xlsx；工作簿结构可打开，关键字段和来源证据存在。
  • outpatient-note-draft：产生10个阶段事件，生成UTF-8 .txt；九字段、青霉素过敏与医生复核提示均存在。
  • followup-plan：产生10个阶段事件，生成UTF-8 .txt；3天后复诊、咳嗽/发热/呼吸观察、血常规/CRP复查、异常提前就医及医生复核均存在。

这3/3只证明当前固定脚本在该详细合成样例上形成闭环，不证明面对所有文件格式、模糊口语或真实病历都能达到100%。

6. 优化方向与下一轮放行条件

P0：修复CLINVEXA上下文预算

  • 自定义端点必须持久化 context_length=65536，探测失败时不得回退到256,000。
  • max_tokens 必须按 上下文上限 - 实际输入tokens - 安全余量 动态计算，并设置合理业务上限；不能把整个上下文窗口当作输出预算。
  • 对约22,617 input tokens的当前系统提示，建议输出预算先限制在2,048–8,192；实际值需按任务分类压测。
  • 修复后验收：新会话固定回复20次，首轮HTTP成功20/20，无400，无重试，P95≤20秒。

P0：加固N260服务

  • 核查模型进程、连接队列、KV Cache、GPU显存、网络路由及超时窗口；保存vLLM与设备监控日志。
  • /v1/models 建议由轻量健康进程稳定响应，不应被长推理阻塞。
  • 对幂等短请求使用有界重试和抖动退避，但发布指标仍按首轮成功率计分。
  • 修复后验收：100次模型发现与100次短生成首轮成功率≥99%；三路并发100次≥99%；零进程重启/OOM。

P0：验证真实64K

  • 用tokenizer准确构造总输入+输出不超过65,536的请求，至少测试32K、48K、60K三个台阶。
  • 每个台阶重复5次；60K首轮成功5/5且P95在约定时限内，才可宣传“64K级上下文可用”。

P1：扩大医疗评测

  • CMExam至少扩大到500–1,000题，并按科目分层，报告宏平均与95%置信区间。
  • 在取得授权后使用脱敏真实病历，由至少两名医生独立标注；计算字段级precision/recall/F1、否定识别、药物剂量、时间线、来源证据覆盖和危险幻觉率。
  • 诊断、处方、剂量或治疗建议的无来源危险事实应为0；所有结果仍需医生复核。
