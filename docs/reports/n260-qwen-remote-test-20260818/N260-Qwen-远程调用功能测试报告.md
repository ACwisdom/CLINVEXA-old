# N260 Qwen 远程调用功能测试报告

测试日期：2026-08-18（Asia/Shanghai）  
测试端点：`http://172.16.0.105:8818/v1`  
模型 ID：`/workspace/model`  
鉴权：无 API Key  
报告性质：工程接入与基础医疗能力测试，不是临床有效性验证

## 一、技术结论

**总体判定：有条件不通过，暂不满足 CLINVEXA 完整 Agent 的发布接入标准。**

远程服务可以发现模型。在显式发送 `chat_template_kwargs.enable_thinking=false` 后，基础对话、JSON 结构化、Tool Calling、流式输出和小样本医疗字段抽取可以工作。但是仍有两个发布阻断项：

1. 服务端真实上下文只有 **8,192 tokens**，低于 CLINVEXA Agent 要求的 **64,000 tokens**。
2. 服务稳定性未达标：正确适配后的 20 例合成医疗工作流通过 19 例；3 路并发 12 次仅成功 9 次；非流式 P95 为 21.052 秒。

本轮没有测试 OCR、ASR、视觉输入、CLINVEXA 完整桌面 UI、2 小时持续压测和真实脱敏临床数据，不能声称这些功能通过。

## 四、测试集与精度计算口径

### 4.1 项目既有测试集

使用项目现有的 20 个 `fully_synthetic` 用例。它们均为纯合成内容，不来自真实患者，覆盖：

- 门诊病历结构化
- 否定语义范围
- 疑似、排除与确诊的确定性
- 过敏史冲突
- 患者本人和家族史区分
- 当前、停用和计划用药
- 检验原值、单位、参考范围和异常标记
- 影像所见与结论分离
- 入院/出院诊断分离
- 相对时间线
- 时间逻辑、性别特异字段、重复文书、OCR 低置信度等质控
- 一页患者摘要、随访计划、多 Agent 路由、无工具降级

每例必须同时满足预设的“必须出现”“禁止出现”和“必须是 JSON 对象”断言才算通过。

### 4.2 本次新增的合成测试

- 8 个固定指令：按规范化后的完全匹配计分。
- 5 份合成病历、45 个字段：按预标注关键词是否出现在对应字段计分。
- 5 个 JSON 请求：按能否解析为单个 JSON 对象计分。
- 5 个 Tool Calling 请求：工具名和全部必填参数均正确才通过。
- 5 个流式请求：状态 200、事件数大于 1、内容正确且出现 `[DONE]` 才通过。
- 3 个推理分离请求：reasoning 与 content 均存在且 content 无思考标签才通过。
- 12 个 3 路并发请求：无超时且固定输出完全正确才通过。

### 4.3 不应误读的“精度”

5 份病历的 100% 是**字段关键词命中率**，不是临床诊断准确率，也不是严格的精确率/召回率/F1。现有 20 例的 95% 是**工作流断言通过率**。没有真实脱敏病例和医生双人标注前，不应对外发布“临床准确率”数字。

## 五、详细失败与恢复测试

### 5.1 8K 上下文是服务端真实限制

`/v1/models` 返回：

```text
model: /workspace/model
max_model_len: 8192
```

实际长上下文请求返回 HTTP 400：输入至少 8,129 token，加 64 个输出 token 后总计至少 8,193，超过模型最大 8,192。由此可确认不是 CLINVEXA 界面识别错误，也不能通过客户端把 Context 强行填写为 65,536 来解决。

### 5.2 默认思考模式会吞掉最终答案

两次初始探针要求只回复 `CLINVEXA_OK`：

- `max_tokens=64`：全部用于英文 reasoning，`content=null`，`finish_reason=length`。
- `max_tokens=512`：仍全部用于英文 reasoning，`content=null`，`finish_reason=length`。

发送 `chat_template_kwargs.enable_thinking=false` 后，1.075 秒返回正确的 `CLINVEXA_OK`。因此 CLINVEXA 的确定性 Skill、JSON 和 Tool Calling 任务应默认关闭思考模式。

### 5.3 20 例中一次超时，但恢复后内容可通过

正确适配后的 20 例中，`SYN-DC-010 relative_time_timeline` 首次读超时 60 秒，导致总成绩为 19/20。服务恢复后，同一用例连续 3 次复测均 HTTP 200，断言完整，延迟为 2.235、2.188 和 2.205 秒。

这说明该例的内容能力可以通过，但服务可用性仍未通过。原始 19/20 不改写为 20/20。

### 5.4 并发和连接稳定性不足

3 路并发的前 3 个请求连接超时，之后 9 个请求成功，首次执行成功率为 75%。另有 1 次推理请求读超时 60 秒。应检查：

- vLLM 请求队列和并发限制
- GPU 显存、KV Cache 和碎片
- 单卡/双卡负载分布
- 模型进程是否重启或 OOM
- 端口前的代理、连接保活和网络丢包

### 5.5 项目旧基准执行器存在适配错误

原样运行项目既有执行器时，40/40 请求均被服务端拒绝：

```text
HTTP 400: System message must be at the beginning.
```

原因是旧执行器把“输出契约”作为第二条 system 消息追加在 user 消息之后。能力复测没有修改测试内容和断言，只把契约合并到首条 system 消息并关闭思考模式。旧执行器兼容性失败和适配后能力结果已分别保存，未混算。

## 六、优化方向

### P0：提升服务端真实上下文

1. 把 vLLM 的 `--max-model-len` 提升到至少 `65536`。
2. 如单 N260 无法为 64K KV Cache 留出显存，评估双 N260 Tensor Parallel。
3. 验收必须同时满足：
   - `/v1/models.max_model_len >= 65536`
   - 实际 64K 输入成功
   - 无 OOM、进程重启或 KV Cache 分配失败

### P0：加固稳定性

1. 保存每次超时对应的 vLLM、GPU、系统和网络日志。
2. 配置健康检查、连接保活、有限请求队列和超时上限。
3. 仅对幂等请求进行有限重试；医疗写入类工具禁止盲目重试。
4. 先完成 100 次 3 路并发，再完成 2 小时持续压测。

### P0：固定 CLINVEXA 请求配置

```json
{
  "chat_template_kwargs": {
    "enable_thinking": false
  }
}
```

- 结构化、Skill、JSON、Tool Calling 默认关闭思考。
- 所有 system 指令必须合并在消息首部。
- 需要展示 reasoning 的任务单独路由，并设置足够输出预算。

### P1：修正基准执行器

- 禁止在 user 消息后追加 system 消息。
- 每个请求的超时必须记录为单例失败，不能终止整轮并丢失证据。
- 报告首次成功率，不以自动重试后的成功掩盖不稳定。

### P2：开展真实医疗验证

获得数据授权后，加入跨科室脱敏病例，由至少两名医生独立标注，计算：

- 字段级精确率、召回率和 F1
- 否定/未提及识别
- 诊断确定性保持率
- 过敏和用药冲突召回率
- 危险事实幻觉率
- 医生修订率和可直接采用率

危险事实幻觉目标应为 0，所有诊断、处置和治疗内容仍须医生复核。

## 七、下一次放行标准

1. 上下文达到 64K，元数据与实际请求一致。
2. 20 个合成医疗工作流 20/20 通过，无超时。
3. JSON、Tool Calling、流式各至少 100 次，成功率 ≥99%。
4. 3 路并发至少 100 次，首次成功率 ≥99%，非流式 P95 ≤20 秒。
5. CLINVEXA 完成“新建会话 → 调用 Skill → 工具执行 → 流式显示 → 结果落盘”的端到端闭环。
6. 保存 2 小时 vLLM、CLINVEXA 网关和 N260 设备监控日志，确认无 OOM、重启和设备故障。
